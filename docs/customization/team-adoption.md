## 권장 시작 지점

[HVE Core 확장](https://marketplace.visualstudio.com/items?itemName=ise-hve-essentials.hve-core)으로 팀 도입을 시작하여 전체 팀원에게 완전한 관리형 컴포넌트 세트를 제공하세요.
팀이 클론 기반 방법을 사용할 준비가 되면, 에이전트에게 포함된 `hve-core-installer` 스킬을 사용하도록 요청하세요. 이 스킬은 환경을 평가하고, 피어 클론·서브모듈·git-ignored 또는 다른 방법을 추천하고, MCP 구성을 안내하며, 에이전트·프롬프트·지침·배포 가능한 스킬 디렉터리 전반에 걸친 전체 또는 맞춤형 선택을 지원합니다.
인스톨러가 제공하는 것을 넘어선 산출물 수정이 필요할 때만 직접 클론 설정으로 전환하세요.

## 도입 전략

HVE Core를 점진적으로 도입하세요. 단계적 접근 방식을 사용하면 팀이 복잡한 산출물로 넘어가기 전에 더 단순한 산출물로 자신감을 쌓을 수 있습니다.

### 1단계: 지침(Instructions)

지침 파일부터 시작하세요. 가장 적은 노력이 필요하며 모든 대화에서 Copilot의 동작을 형성하여 즉각적인 가치를 제공합니다. 팀의 코딩 표준, 커밋 메시지 형식, PR 규칙을 다루는 두세 개의 지침을 작성하세요.

### 2단계: 에이전트와 프롬프트

팀이 지침에 익숙해지면, 반복 가능한 워크플로(코드 리뷰, 조사 작업, 구현 패턴)를 위한 커스텀 에이전트와 일회성 작업(보일러플레이트 생성, 출력 포맷)을 위한 프롬프트를 도입하세요.

### 3단계: 스킬과 공유 배포

복잡한 다단계 워크플로를 위해 도메인 지식을 스킬로 패키징하세요. 관련 산출물을 패키지 범위의 `.github` 경로 아래에 배치하고 관리형 배포를 위해 루트 `plugin.json`을 동기화하거나, 저장소 소유의 부분 집합을 위해 선택적 클론을 사용하세요.

### 도입 진행 상황 측정

관찰 가능한 지표를 통해 도입을 추적하세요:

* 일상 업무에서 커스텀 에이전트를 사용하는 팀원 수
* 지침 및 프롬프트 호출 빈도
* 반복적인 수동 작업 감소
* 생성된 코드와 문서의 품질 향상

## 네이밍 규칙

일관된 네이밍은 산출물을 쉽게 찾고 그 목적을 한눈에 명확하게 만듭니다. 전체적으로 케밥 케이스(kebab-case) 패턴을 따르세요.

### 파일 네이밍 패턴

| 산출물 유형  | 패턴                                        | 예시                         |
|----------------|------------------------------------------------|----------------------------------|
| Instructions   | `{topic}.instructions.md`                      | `python-script.instructions.md` |
| Agents         | `{workflow}.agent.md`                          | `code-review.agent.md`          |
| Prompts        | `{action}.prompt.md`                           | `generate-tests.prompt.md`      |
| Skills         | `{skill-name}/SKILL.md`                        | `pr-reference/SKILL.md`         |
| Manifest paths | Plugin manifest와 `docs/plugins/hve-core.md` | `agents/ado/example.agent.md`   |

### 네임스페이스 ID

네임스페이스 ID는 `.github/` 전체에서 관례적인 디렉터리 이름 역할을 하며, 고유하고, 소문자이고, 케밥 케이스여야 합니다. 이들은 소스를 조직화하며 독립적으로 설치 가능한 마켓플레이스 제품을 만들지 않습니다. 네임스페이스가 서비스하는 도메인이나 팀을 반영하는 ID를 선택하세요:

* Azure DevOps 통합을 위한 `ado`
* 언어별 규칙을 위한 `coding-standards`
* 보안 아키텍처 워크플로를 위한 `security`

### 디렉터리 구성

산출물을 적절한 `.github/` 하위 디렉터리의 네임스페이스 ID 아래에 배치하세요:

```text
.github/
  agents/{package-id}/
  instructions/{package-id}/
  prompts/{package-id}/
  skills/{package-id}/
```

하위 디렉터리 없이 `.github/agents/`, `.github/instructions/`, `.github/prompts/`, `.github/skills/`의 루트에 있는 산출물은 저장소 전용으로 처리되며 플러그인 멤버십과 확장 패키징에서 제외됩니다.

## 거버넌스 모델

### 소유권

각 산출물 카테고리에 명확한 소유권을 지정하세요:

* 지정된 유지관리자 또는 팀이 `hve-core` 플러그인 내 각 컴포넌트 네임스페이스를 소유합니다
* 여러 도메인에 걸쳐 있는 개별 지침 파일은 별도의 소유자를 가질 수 있습니다
* 저장소 루트의 `copilot-instructions.md` 파일은 횡단적 관심사를 반영하며 더 넓은 범위의 리뷰가 필요합니다

### 리뷰와 승인

Copilot 커스터마이징 파일을 프로덕션 코드와 동일한 엄격함으로 다루세요:

* 지침, 에이전트, 스킬 변경 시 풀 리퀘스트 리뷰를 요구하세요
* CODEOWNERS를 사용하여 리뷰를 산출물 소유자에게 라우팅하세요
* 병합 전에 `npm run validate:local`로 변경 사항을 검증하세요
* 배포 가능한 멤버십을 변경한 후 `npm run plugin:sync`와 `npm run plugin:validate`를 실행하세요

### 상충되는 지침 처리

여러 지침 파일이 모순되는 안내를 제공할 때, 해결 순서는 다음과 같습니다:

1. `copilot-instructions.md`의 최우선순위 규칙이 모든 것을 재정의합니다
2. 더 구체적인 `applyTo` 패턴이 더 넓은 패턴보다 우선합니다
3. 동일한 구체성을 가진 두 지침이 충돌할 때, 산출물 소유자가 풀 리퀘스트를 통해 충돌을 해결합니다

## 신규 팀원 온보딩

### 단계별 온보딩

1. 신규 팀원에게 설치를 위한 [시작하기](../getting-started/README.md) 가이드를 안내하세요.
2. 기존 에이전트를 사용한 첫 상호작용을 안내하세요(RPI 워크플로가 좋은 시작점입니다).
3. 지침 파일을 함께 편집하며 Copilot 동작을 어떻게 형성하는지 보여주세요.
4. 팀의 커스텀 에이전트를 소개하고 각각을 언제 사용할지 설명하세요.
5. 팀의 네이밍 규칙과 거버넌스 기대치를 공유하세요.

### 첫 번째 커스터마이징 실습

온보딩 연습으로 신규 팀원이 첫 지침 파일을 만들도록 하세요. 간단한 코딩 스타일 지침이 적합합니다:

1. 최소한의 프런트매터(`description`과 `applyTo` 필드)를 가진 `.github/instructions/{package-id}/my-style.instructions.md` 파일을 생성하세요
2. `hve-builder`를 create 모드로 실행하고 기존 팀 지침을 알려진 참조로 제공하세요
3. HVE Builder의 정적 결과, 행동 테스트 결과, 호스트 검증 결과를 검토하세요
4. 실행 가능한 발견 사항이 소스 변경을 필요로 한다면 승인된 improve 실행을 계속하세요
5. Copilot 채팅을 열고 지침이 응답에 영향을 미치는지 확인하여 테스트하세요
6. 팀의 PR 프로세스에 따라 파일을 리뷰를 위해 제출하세요

> [!TIP]
> 첫 커스터마이징을 하는 동안 신규 팀원을 경험 있는 사람과 짝지으세요. HVE Builder가 산출물을 작성하고 검증하는 방법을 보는 것은 전체 작성 워크플로에 대한 직관을 키워줍니다.

## 변화 관리

### 새 산출물 도입

새로운 지침, 에이전트, 스킬을 추가할 때 구조화된 프로세스를 따르세요:

1. 기능 브랜치에서 최소한의 프런트매터로 산출물 파일을 생성하세요
2. 관련된 알려진 참조와 함께 `hve-builder`를 create 또는 improve 모드로 실행하세요
3. 전체 결과가 통과할 때까지 정적, 행동, 검증 게이트를 해결하세요
4. `npm run validate:local`을 실행하여 로컬에 안전한 검사를 검증한 다음, 관련 CI 전용 레인을 별도로 재현하세요
5. 사용자에게 보이는 표면이 변경되면 `npm run plugin:sync`를 실행하고 `docs/plugins/hve-core.md`를 업데이트하세요
6. `npm run plugin:validate`와 `npm run docs:generate:check`를 실행하세요
7. 산출물이 하는 일과 그 이유에 대한 명확한 설명과 함께 풀 리퀘스트를 제출하세요

### 커뮤니케이션 패턴

팀 워크플로에 영향을 미치는 변경 사항을 알리세요:

* 새 에이전트: 에이전트 이름, 목적, 호출 예시를 공유하세요
* 수정된 지침: 무엇이 바뀌었고 왜 바뀌었는지 설명하세요
* 폐기된 산출물: 마이그레이션 단계와 일정을 제공하세요

### 폐기 워크플로

산출물을 폐기하려면:

1. `hve-builder`의 improve 모드를 사용하여 대체 산출물을 가리키는 폐기 공지를 추가하세요.
2. 폐기를 알리고 마이그레이션 일정을 제공하세요.
3. 관리형 배포에서 제외해야 할 때 산출물을 `.github/deprecated/` 아래로 옮기세요.
4. `npm run plugin:sync`와 `npm run plugin:validate`를 실행하세요. 매니페스트 변경은 Stable과 PreRelease에서 함께 제거됩니다.
5. 합의된 전환 기간 후 보관된 산출물을 제거하세요.

## 역할 기반 도입 경로

각 역할은 서로 다른 수준에서 커스터마이징에 진입합니다. 이 경로는 아홉 가지 역할 각각에 대한 시작점과 진행 방향을 제공합니다.

### Engineer

1. 팀의 코딩 표준에 대한 지침 파일을 생성하세요
2. 가장 흔한 코드 리뷰 패턴을 위한 커스텀 에이전트를 구축하세요
3. 스크립트와 참조를 포함한 스킬로 도메인 지식을 패키징하세요

### TPM (Technical Program Manager)

1. RPI 워크플로를 사용하여 프로젝트 상태를 조사하고 문서화하세요
2. 상태 보고서와 위험 요약을 생성하는 프롬프트를 작성하세요
3. 팀 간 종속성을 추적하는 에이전트를 구축하세요

### Tech Lead

1. 아키텍처 결정 규칙에 대한 지침을 작성하세요
2. 팀 표준을 강제하는 코드 리뷰 에이전트를 만드세요
3. 팀의 워크플로를 담아내는 검토된 맞춤형 선택을 수립하세요

### Security Architect

1. 보안 모델 분석을 위한 보안 중심 지침을 추가하세요
2. 일반적인 취약점을 확인하는 보안 리뷰 에이전트를 만드세요
3. 보안 스캐닝 도구와 통합되는 스킬을 구축하세요

### Data Scientist

1. 노트북 규칙과 데이터 처리에 대한 지침을 만드세요
2. 탐색적 데이터 분석 패턴을 위한 프롬프트를 구축하세요
3. 참조 데이터셋을 포함한 스킬로 통계 방법론을 패키징하세요

### SRE/Operations

1. 런북 형식과 인시던트 대응에 대한 지침을 작성하세요
2. 인프라 리뷰 워크플로를 위한 에이전트를 만드세요
3. 모니터링, 알림, 배포 도구를 통합하는 스킬을 구축하세요

### Business PM (Product Manager)

1. 프롬프트를 사용하여 요구사항으로부터 사용자 스토리 초안을 생성하세요
2. 요구사항 분석을 위한 에이전트를 만드세요
3. 커스텀 에이전트로 Design Thinking 워크플로를 구축하세요

### New Contributor

1. [시작하기](../getting-started/README.md) 가이드를 따라 첫 상호작용을 완료하세요
2. 위의 온보딩 실습으로 첫 지침 파일을 만드세요
3. 식별한 워크플로 격차에 대한 새로운 에이전트나 스킬을 제안하세요

### Utility

1. 수정 없이 기존 프롬프트와 에이전트를 사용하세요
2. 특정 워크플로 맥락에 맞게 지침을 커스터마이징하세요
3. 사용 패턴을 기반으로 공유 컴포넌트 개선에 기여하세요

## 성공 측정

### 정량적 지표

* 산출물 수: 시간 경과에 따른 지침, 에이전트, 스킬의 수를 추적하세요
* 호출 빈도: 팀원이 커스텀 에이전트와 프롬프트를 얼마나 자주 활성화하는지 모니터링하세요
* 오류 감소: 커스터마이징이 대상으로 하는 일반적인 실수에 대한 전후 비율을 측정하세요
* 온보딩 속도: HVE Core를 사용하는 팀원과 그렇지 않은 팀원의 생산성 도달 시간을 비교하세요

### 정성적 지표

* 팀 자신감: AI 지원 워크플로로 더 효과적이라고 느끼는지 설문하세요
* 일관성: 생성된 출력(코드, 문서, PR)이 팀 규칙을 더 안정적으로 따르는지 검토하세요
* 피드백 품질: Copilot 제안이 더 적은 수동 수정을 필요로 하는지 평가하세요

### 피드백 수집

정기적인 피드백 주기를 수립하세요:

* 스프린트 회고에 Copilot 커스터마이징 효과를 포함하세요
* 커스터마이징 격차를 보고하기 위한 공유 채널이나 문서를 유지하세요
* 누적된 피드백을 기반으로 분기별로 산출물을 검토하고 조정하세요
* 거의 사용되지 않는 산출물을 추적하고 폐기를 고려하세요
