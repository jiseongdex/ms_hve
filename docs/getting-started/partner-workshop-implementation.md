## 워크샵에서 솔루션 구현으로

가장 간단한 설정은 구현 대상 프로젝트 저장소에 HVE Core VS Code 확장을
설치하는 것입니다. 이 확장은 HVE 에이전트인 RPI Agent와 `/rpi`,
`/rpi-research`, `/rpi-plan`, `/rpi-implement`, `/rpi-review`를 관리합니다.
또한 컨텍스트를 보존하기 위해 .copilot-tracking을 대상 프로젝트 저장소로
복사하고, Microsoft Partner 전용 커스텀 에이전트와 스킬을 위해 이 저장소의
.github 파일도 복사하세요.

다음 중 하나의 옵션을 선택하려면 [HVE Core 설치하기](install.md)를
따르세요:

| 상황 | 권장 설정 |
|---|---|
| VS Code를 사용하는 대부분의 팀 | HVE Core VS Code 확장 설치 |
| Copilot CLI를 사용하는 팀 | `hve-core` 플러그인 설치 |
| 아티팩트를 소유하고 커스터마이즈해야 하는 팀 | 선택적 클론 방식 사용 |

팀이 해당 파일을 유지보수할 의도가 없다면 전체 HVE 저장소를 제품
저장소로 복사하지 마세요.

설치 후:

1. VS Code에서 구현 저장소를 여세요.
2. GitHub Copilot Chat을 여세요.
3. **RPI Agent**를 선택하거나 직접 단계별 명령을 사용하세요.

초기 리서치와 계획은 이미 완료되었으므로, 다음 단계에서는
/rpi-implement와 /rpi-review를 사용하세요.

## 1A 단계: 새 프로젝트 시작

워크샵 결과물이 새로운 애플리케이션이나 서비스가 될 때 이 경로를
사용하세요.

1. 저장소를 만들고 VS Code에서 루트를 여세요.
2. Hypervelocity Innovation GitHub 에이전트와 스킬인 .github/*를
   저장소로 복사하세요.
3. HVE Core를 설치 또는 활성화하세요 ([HVE Core 설치하기](install.md)
   참고).
4. 워크샵 결과물을 검토, 업데이트, 승인하세요.

   * 검토된 아티팩트만 일치하는 `.copilot-tracking/` 폴더 아래 새
     저장소에 복사하세요(동일한 상대 하위 경로 유지):
     * `.copilot-tracking/research/{{YYYY-MM-DD}}/*-research.md`
     * `.copilot-tracking/brd-sessions/*.md`
     * `.copilot-tracking/prd-sessions/*.md` 및 `*.state.json`
     * `.copilot-tracking/dt/**/experience-draft.md`
     * `.copilot-tracking/plans/{{YYYY-MM-DD}}/*-plan.md`
     * `.copilot-tracking/github-issues/prds/**/issues-plan.md` 및
       `handoff.md`
     * `.copilot-tracking/details/{{YYYY-MM-DD}}/*-implementation-plan.md`
       (해당하는 경우 Marketplace 및 Agent Store 준비 상태)
     * `.copilot-tracking/details/{{YYYY-MM-DD}}/solution-monetization-plan.md`
       (해당하는 경우 미해결 결정과 승인 상태를 포함한 공유 상용화 기록)

   * `.copilot-tracking/sandbox/`, `.copilot-tracking/challenges/`, 또는
     검토되지 않은 작업 파일은 복사하지 마세요. 검토되고 승인된
     아티팩트만 핸드오프에 포함됩니다.

5. 구현을 시작하기 전에 리서치와 계획의 준비 상태를 확인하세요. 다음
   단계로 진행하기 전에 모든 공백을 해결하세요. 계획이나 PRD가
   `Blocked` 또는 `Not ready` 상태를 기록하고 있는 동안에는
   `/rpi-implement`를 시작하지 마세요.
6. 계획이 아직 개념적이라면 `/rpi-plan`을 한 번 실행하여 새 저장소에
   맞게 조정하세요. 제품 디스커버리를 반복하지 마세요.
7. 프로젝트 매니저가 첫 번째 구현 작업 승인을 퍼실리테이션합니다.
   * 지정된 책임 담당자(제품, 기술 리드, 또는 딜리버리 담당자)가
     계획의 첫 번째 P0 작업을 5단계의 준비 상태 확인과 비교하여
     검토합니다.
   * 담당자는 이 작업이 구현 승인되었음을 서면으로(댓글, 계획에서 체크된
     박스, 또는 `planning-log.md`나 백로그 항목의 메모) 확인하며, 날짜와
     승인자 이름을 포함합니다.
   * 계획이나 PRD에 이 작업을 포함하는 체크되지 않은 사람 검토 체크박스가
     있다면, 승인 전에 거기에 지정된 검토자가 체크해야 합니다. 에이전트가
     대신 체크해서는 안 됩니다.
   * "계획이 완료된 것처럼 보인다"를 승인으로 취급하지 마세요. 5단계의
     모든 체크리스트 항목이 준비되어 있더라도 승인에는 명시적인 사람의
     결정이 필요합니다.
8. `/rpi-implement`를 실행하세요.

다음 프롬프트를 사용하세요: (당일 워크샵에서는 생략합니다)

```text
/rpi-implement
승인된 구현 계획을 활용하여, 이 새로운 리포지토리에서 승인된 첫 번째 P0 작업만 구현하십시오.
계획에 필요한 최소한의 프로젝트 구조를 생성하고, 리포지토리 지침을 준수하며, 계획된 수용 기준(acceptance criteria)과 기존 검증 명령을 사용하십시오.
이 작업과 관련된 경우, 연결된 공유 솔루션 수익화 계획에 명시된 승인된 상업적 결정을 준수하십시오.
단, 제안된 조건들을 확정된 규칙으로 간주하여 구현하지는 마십시오.
구현 증거는 .copilot-tracking/changes/ 경로에 기록하십시오.
연기된 작업이나 배포 관련 활동은 구현하지 마십시오.
```

당일 워크샵을 위해 UX 중심의 구현을 검증합니다.

```text
현재 계획된 내용에 기반해서 UX 테스트 용으로 Local PC 에서 실행되는 코드를 작성해 줄 수 있나요?
작성 가능한 범위를 알려주세요.
```

검증 가능한 범위 답변을 기반으로 UX 테스트를 구현하세요.
샘플 프롬프트 입니다.

```text
/rpi-implement

운영용 MVP와 분리된 로컬 UX 테스트용 프로토타입으로 코드를 .copilot-tracking/ux-test/ 경로에 작성해 주세요.
미정인 기술·정책을 확정하지 않고, 합성 데이터와 모의 응답으로 사용자 흐름을 검증하는 범위입니다.

UX 경험 초안은 다음을 기준으로 작성합니다.
  - 영역 : 로컬에서 테스트할 내용
  - 고객 검색 및 조회 : 이름·전화번호 검색, 목록·상세, 선택 상태, 무결과
  - 고객 정보 관리 : 생성·수정·취소, 저장 후 재조회, 중복 전화번호 오류와 입력 보존
  - 계좌 등록·집계 : 세 필수값 검증, 명시적 잔액 0 허용, 번호 수정·삭제 금지, 고객별·계정 유형별 합계

권장 구현 방식
  - React + TypeScript 기반 웹 화면을 로컬 PC의 브라우저에서 실행
  - 실제 고객정보 없이 합성 데이터만 사용
  - 브라우저 로컬 저장으로 새로고침 후 데이터 유지 및 초기화 지원
  - 미정인 필드·계정 유형·통화 등은 테스트용 가정으로 별도 기록

이는 제안하는 테스트 구성이지 운영 기술 스택의 확정은 아닙니다.

이 범위에서 검증하지 않는 것
  - Azure SQL의 실제 UNIQUE·NOT NULL·동시 저장 보장
  - 실제 인증·테넌트 격리·서버 권한 통제
  - 실제 AI 정확성·금융 정책 적합성
  - 운영 성능·보안·규제 준수
  - Marketplace 과금·활성화·배포·게시

특히 중복 오류나 권한 거부 화면을 재현하는 것은 실제 DB·보안 검증과 다릅니다. 
가격·좌석 수·AI 사용량 제한 같은 미승인 상업 조건도 넣지 않습니다.

UX 경험 첫 범위는 고객 검색 → 정보 수정 → 계좌 등록의 한 흐름입니다. 
관련 수용 기준을 UX 검증과 실제 통합 검증으로 구분하고, 
구현 증거는 .copilot-tracking/changes/ 경로에 기록하십시오.
```

## 1B 단계: 기존 프로젝트에서 계속하기

워크샵이 기존 제품에 기능을 추가하는 경우 이 경로를 사용하세요.

1. VS Code에서 현재 저장소를 여세요.
2. Hypervelocity Innovation GitHub 에이전트와 스킬인 .github/*를
   저장소로 복사하세요.
3. HVE Core를 설치 또는 활성화하세요 ([HVE Core 설치하기](install.md)

   * 호환 가능한 동작을 보존하세요

다음 프롬프트를 사용하세요: (당일 워크샵에서는 생략합니다)

```text
/rpi-implement
승인된 구현 계획을 활용하여, 본 저장소에서 승인된 첫 번째 P0 작업만 구현하십시오.
기존 구성 요소를 재사용하고, 현재의 코드 및 테스트 관례를 준수하며, 변경 사항은 계획된 동작 범위 내로 제한하십시오.
본 작업과 관련된 경우, 연결된 '공유 솔루션 수익화 계획'에 명시된 승인된 상업적 결정을 존중하십시오. 
단, 제안된 조건들을 확정된 규칙으로 간주하여 구현하지는 마십시오.
변경 사항을 검증할 수 있는 최소한의 기존 검증 명령을 실행하고, 구현 근거를 .copilot-tracking/changes/ 디렉토리에 기록하십시오.
추후로 미뤄진 작업이나 배포 관련 활동은 구현하지 마십시오.
```

워크샵이 다른 패턴을 제안했다는 이유만으로 동작하는 아키텍처를 교체하지
마세요. 중대한 차이점은 기록하고, 범위, 요구사항, 종속성이 바뀌는 경우
`/rpi-plan`으로 돌아가세요.

## 2단계: 하나의 작업 구현

구현 중에는:

1. 승인된 계획을 종속성 순서대로 따르세요.
2. 한 번에 하나의 백로그 스토리 또는 계획 작업만 진행하세요.
3. 요구사항과 수락 기준을 계속 확인 가능한 상태로 유지하세요.
4. 동작과 함께 테스트를 추가하거나 업데이트하세요.
5. 각 변경 사항을 다루는 가장 작은 기존 검증 명령을 실행하세요.
6. 편차, 발견 사항, 검증 결과를 구현 변경 기록에 남기세요.
7. 발견 사항이 범위, 아키텍처, 보안, 개인정보 보호, 책임 있는 AI, 사용자
   행동, 가격, 라이선스, 유료 접근 규칙을 변경한다면 중단하고 계획으로
   돌아가세요. 상업적 변경 사항은 제품 매니저에게 전달하고, 종속 동작을
   구현하기 전에 공유 상용화 계획을 업데이트하세요.

구현 단계는 계획과 저장소가 뒷받침하는 범위 내에서 지역적인 엔지니어링
결정을 내릴 수 있습니다. 누락된 비즈니스 규칙, 권한, 성공 목표, 게시 관련
주장을 만들어내서는 안 됩니다.

## 3단계: 결과 검토

구현과 검증이 완료된 후 `/rpi-review`를 실행하세요.

다음 프롬프트를 사용하세요:

```text
/rpi-review
완료된 구현 사항을 다음 항목들과 대조하여 검토하십시오.
- 승인된 구현 계획
- 제품 요구사항 정의서(PRD) 및 해당 수용 기준(Acceptance Criteria)
- 구현 변경 기록
- 리포지토리의 기존 관례 및 검증 결과

UX 경험 테스트에서 의도한 성과를 제공하는지 확인하십시오.
기능적 격차, 회귀(regression) 현상, 보안 또는 개인정보 보호 관련 우려 사항, 접근성 문제, 승인되지 않은 편차, 그리고 후속 작업이 필요한 부분을 파악하십시오.
```

검토는 다음 질문에 답해야 합니다:

* 구현이 범위 내 모든 수락 기준을 충족했는가?
* 권한과 데이터 경계를 보존했는가?
* 인용, 불확실성, 실패, 사람의 결정이 올바르게 표현되었는가?
* 테스트와 검증 결과가 완료 주장을 뒷받침하는가?
* 구현이 계획에서 벗어났는가?
* 상업적 동작이 범위에 있다면, 포함된 사용량을 중복 청구하지 않고
  승인된 패키지, 자격, 청구 결정과 일치하는가?
* 어떤 발견 사항이 완료를 막는가?
* 어떤 항목이 이후 마일스톤에 속하는가?

검토에서 차단 결함이 발견되면 구체적인 발견 사항과 함께
`/rpi-implement`로 돌아가세요. 수정과 관련 검증이 완료된 후에만
`/rpi-review`를 다시 실행하세요.

## 4단계: 마일스톤 마감

검토를 통과하면:

1. 구현과 검토 증거가 프로젝트와 함께 저장되었는지 확인하세요.
2. 백로그 항목을 완료된 수락 증거로 업데이트하세요.
3. 지연된 작업을 명시적인 후속 항목으로 옮기세요.
4. 사람 검토자에게 풀 리퀘스트 또는 마일스톤 승인을 요청하세요.
5. 저장소의 일반 검토 절차를 통해 병합하세요.
6. 남은 승인된 백로그로 다음 마일스톤을 시작하세요.

검토자를 대신하여 사람 검토 체크박스를 완료로 표시하지 마세요.

## 5단계: 게시 준비 상태 재평가

Marketplace와 Agent Store 준비 상태는 MVP 완료와는 별개입니다.

MVP 검토 후:

1. 검증된 제품 동작으로 Marketplace와 Agent Store 준비 아티팩트를
   업데이트하세요.
2. 워크샵 당시의 메모에 의존하지 말고 현재 Microsoft 가이드를
   확인하세요.
3. Partner Center와 테넌트 상태를 권위 있는 시스템에서 확인하세요.
4. 패키지, 아이덴티티, 라우팅, 수명 주기, 보안, 개인정보 보호, 접근성,
   지원, 제거 테스트를 완료하세요.
5. 측정된 전달 비용, 패키지 제한, 자격, 별도 고객 청구를 공유 상용화
   계획에서 조정하세요. 가격을 승인하거나 상업적 조건을 구성하기 전에
   제품 매니저, 재무, 기타 필요한 검토를 받으세요. 미해결된 결정은
   미결로 유지하세요.
6. 게시자가 통제하는 준비 상태를 인증, 게시, 공동 판매 상태와 별개로
   유지하세요.
7. 책임 담당자가 해당 게이트를 승인한 후에만 제출하거나 게시하세요.

검증된 MVP에 비추어 준비 상태를 재평가하려면 다음 프롬프트를
사용하세요:

```text
.copilot-tracking/details/ 디렉터리에 있는 마켓플레이스 및 에이전트 스토어 준비 상태 아티팩트를 .copilot-tracking/changes/ 디렉터리에 있는 구현 및 검토된 MVP 증거와 비교하여 검토합니다.
해당 아티팩트에서 링크된 공유 솔루션 수익화 계획을 포함하고, 별도의 가격표를 작성하는 대신 해당 계획에서 상업적 결과를 조정합니다. 
아직 해결되지 않은 준비 게이트(제품, 기술, 상업, 파트너 센터, 거버넌스, 컴패니언 에이전트)를 식별하고, 버전 관련 사항에 대한 최신 Microsoft 지침을 확인하고, 각 미해결 게이트에 대한 담당자와 다음 조치를 명시합니다.
증거 없이 게이트를 준비 완료로 표시하거나, 어떤 내용도 제출 또는 게시하지 마십시오.
```

게시 워크플로우는
[Microsoft Marketplace 및 Copilot Agent Store 준비](partner-workshop-publishing.md)를
참고하세요.
